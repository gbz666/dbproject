# 进阶技术概览：Elasticsearch、锁 等

这里用通俗方式说明几类「听起来高大上」的技术是什么、用在什么场景，以及在你当前项目里要不要上、怎么写进简历。

---

## 1. Elasticsearch（全文检索 / 搜索引擎）

### 是什么
- 一个基于 **Lucene** 的 **分布式搜索与分析引擎**，常用来做：
  - **全文检索**：按关键词搜文档、商品、订单号、客户名等，支持分词、高亮、拼音、纠错。
  - **日志/指标分析**：配合 Logstash、Kibana 做 ELK 日志分析、监控大屏。
  - **复杂聚合**：多维度统计、漏斗、分布（如按地区/时间统计订单）。

### 和 MySQL 的区别
- **MySQL**：适合「精确查一条、按主键/索引查、简单条件」；模糊 `LIKE '%xx%'` 在大数据量下慢且难优化。
- **Elasticsearch**：适合「模糊搜、多条件组合、高亮、排序、聚合」，数据通常会从 MySQL 同步或双写过去。

### 在你项目里适合做什么
- **客户/供应商/产品/订单的「全局搜索」**：例如一个搜索框，输入关键词同时搜客户名、订单号、产品名，返回高亮结果。  
  实现方式：把需要被搜的实体（客户、产品、销售订单等）在新增/修改时同步到 ES 里建索引，前端调 ES 的搜索接口（或经后端封装）做查询。

### 简历可以怎么写
- 「使用 Elasticsearch 实现客户/订单/产品的全文检索与高亮展示」
- 「将业务数据同步至 ES，支持多条件组合查询与聚合统计」

### 学习成本
- 中等：要理解索引、mapping、分词器、常用 query/agg。  
  若只是课设/简历加分，可以只做「一个搜索接口 + 一个索引」，不必上集群、复杂聚合。

## 2. 「上锁」——乐观锁 vs 悲观锁 vs 分布式锁

### 乐观锁（Optimistic Lock）
- **是什么**：不加真正的锁，在表里加一个 **版本号/时间戳** 字段，更新时 `WHERE id = ? AND version = ?`，若影响行数为 0 说明被别人改过了，就提示「数据已被修改，请刷新后重试」。
- **典型场景**：编辑一条订单、一个客户、一条库存记录时，防止多人同时改同一条导致覆盖。
- **在你项目里**：给「销售订单、采购订单、库存」等表加 `version` 字段，更新时在 Service 里先查再更新并校验 version，非常适合写进简历。
- **简历**：「使用乐观锁（version 字段）解决并发更新覆盖问题」

### 悲观锁（Pessimistic Lock）
- **是什么**：真正在数据库里加锁，例如 `SELECT ... FOR UPDATE`，这条行被当前事务锁住，别人要改得等当前事务提交或回滚。
- **典型场景**：扣库存、抢单等「强一致、不能超卖」的场景。
- **在你项目里**：例如「出库/入库扣减库存」时，对库存行 `SELECT ... FOR UPDATE` 再扣减，避免超卖。
- **简历**：「使用悲观锁（FOR UPDATE）保证库存扣减的并发安全」

### 分布式锁（一般用 Redis）
- **是什么**：多台服务器或多个服务同时抢「同一把锁」，只有拿到锁的能执行某段逻辑（如发奖、调第三方接口限流），用 **Redis** 的 `SET key value NX EX 秒数` 或 Redisson 的锁实现。
- **典型场景**：定时任务只跑一台、防止重复支付、接口限流（同一用户/同一单不能并发执行）。
- **在你项目里**：例如「同一订单不允许重复出库」：出库前用 Redis 锁 `outbound:orderId:123`，拿到锁再执行，执行完释放锁。
- **简历**：「基于 Redis 实现分布式锁，保证订单出库等操作的幂等与互斥」

## 3. 小结：怎么选、怎么写简历

| 技术           | 在你项目里的典型用法           | 简历一句式 |
|----------------|--------------------------------|------------|
| Elasticsearch  | 客户/产品/订单 全局搜索 + 高亮 | 使用 ES 实现全文检索与多条件组合查询 |
| 乐观锁         | 订单/库存表加 version，防覆盖  | 使用乐观锁解决并发更新覆盖问题       |
| 悲观锁         | 出库/入库时库存行 FOR UPDATE   | 使用悲观锁保证库存扣减并发安全       |
| Redis 分布式锁 | 订单出库/关键操作互斥、防重复 | 基于 Redis 分布式锁保证操作幂等与互斥 |

建议优先做其中 1～2 项（例如 **乐观锁 + 一个 ES 搜索**），既能体现「并发」「检索」两个方向，又不会把课设搞得太重。  
若你愿意，我可以按「先加乐观锁」或「先接 ES 搜索」给你列具体改表、改接口、改前端的步骤（按你项目现有结构来写）。
